Vector databases & Chroma DB

Story spine for Module 1. Theory first, then metrics by hand, then Chroma does the same job at scale. Source map: docs/MODULE1_SOURCE_MAP.md

One-line story: Turn messy data into numbers (vectors) → store them so “nearby” means “similar” → search with distance metrics → use Chroma so you don’t brute-force everything.

Why this exists (RAG link)

In RAG you retrieve useful chunks before the LLM writes. Retrieval quality depends on embeddings + a store that can find nearest neighbors fast. That store is the vector database. 

Source → embed → vectors in DB → query embed → nearest chunks → prompt → LLM

Vector DB vs traditional DB

FunctionTraditionalVector
ShapeTables / rows / columnsHigh-dimensional vectors
SearchSQL exact / joinsSimilarity / nearest neighbor
IndexB-trees, etc.HNSW, LSH, metric trees…
Sweet spotTransactions, structured business dataText, images, recs, RAG context
Trap: a vector library (in-memory search helpers) ≠ a full vector database (CRUD, persistence, production ops).

Three metrics (cheat sheet)

MetricCares about magnitude?Best for (course)
L2 (Euclidean) yes Spatial / geometric closeness
Cosine no — direction / angle Text & embeddings (topic match)
Dot product yes Topic + “strength” (e.g. popularity) 
cosine_distance = 1 − cosine_similarity
Chroma spaces often: l2 (default) · cosine · ip (inner product)

Chroma mental model

create collection
  → add documents (+ optional metadata / precomputed embeddings)
  → Chroma embeds (or you pass embeddings)
  → query(text or vector) → top-k nearest
  → optional filters: where (metadata) · where_document (text)

Under the hood Chroma uses HNSW (approximate nearest neighbor) so it does not always compare the query to every vector. Deploy: standalone (one process) or client–server.
